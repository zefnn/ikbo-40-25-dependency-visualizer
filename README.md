# Визуализатор графа зависимостей (ИКБО-40-25, Вариант №10)

Учебный проект по дисциплине «Конфигурационное управление».
Инструмент визуализации графа зависимостей для менеджера пакетов
Python (pip). Готовые средства получения зависимостей (менеджеры
пакетов, сторонние библиотеки) не используются. Разработка ведётся
поэтапно; текущее состояние соответствует **Этапу 4 (дополнительные
операции)**.

## Общее описание

Приложение — консольная утилита (CLI) на Python 3, написанная только
на стандартной библиотеке. Все параметры, которые настраивает
пользователь, задаются в конфигурационном файле формата INI
(Этап 1). Данные о зависимостях приложение берёт из репозитория
пакетов (PyPI JSON API) и само разбирает строки зависимостей в
формате PEP 508 (Этап 2). Из этих данных строится граф зависимостей
с учётом транзитивности: обход в ширину (BFS) без рекурсии, фильтр
пакетов по подстроке, обнаружение циклов, а вместо настоящего
репозитория можно подставить тестовый — текстовый файл с графом
(Этап 3). Для тестового репозитория можно вывести и обратные
зависимости — пакеты, которые зависят от заданного; они ищутся тем
же обходом в ширину (Этап 4). Ошибки конфигурации и репозитория
выводятся понятными сообщениями, а не трассировками.

## Структура репозитория

```text
config.ini          пример конфигурации (requests 2.32.3 с PyPI)
run.sh              скрипт запуска приложения
requirements.txt    зависимости для запуска тестов (pytest)
pyproject.toml      настройки pytest
src/depvis/         исходный код приложения
tests/              модульные тесты (pytest), работают без сети
examples/           примеры конфигураций, тестовые репозитории и
                    демонстрационные скрипты
```

## Функции и настройки

### Запуск

```text
./run.sh [-h] [-c CONFIG]
```

- `-c CONFIG`, `--config CONFIG` — путь к INI-файлу конфигурации
  (по умолчанию `config.ini` в текущем каталоге);
- `-h`, `--help` — справка.

Других аргументов нет: все настройки берутся из файла конфигурации.

### Этап 1 — конфигурация

Файл в кодировке UTF-8 (допускается BOM) содержит ровно одну секцию
`[settings]` со всеми восемью параметрами (восьмой —
`reverse_dependencies`, он добавлен на Этапе 4):

```ini
[settings]
package_name = requests
repository = https://pypi.org/pypi
test_mode = false
version = 2.32.3
output_image = graph.png
ascii_tree = false
filter_substring =
reverse_dependencies = false
```

- Значение отделяется от имени только знаком `=`.
- Строки, начинающиеся с `;` или `#`, — комментарии.
- Имена параметров не зависят от регистра, имя секции — зависит.
- Символ `%` в значениях не имеет особого смысла (интерполяция
  `configparser` отключена), поэтому URL вида `%20` допустимы.
- Относительные пути отсчитываются от текущего рабочего каталога.

Параметры:

- **`package_name`** — имя анализируемого пакета. В обычном режиме —
  имя pip-пакета по PEP 508: латинские буквы, цифры, `.`, `_`, `-`;
  начинается и заканчивается буквой или цифрой (`requests`,
  `zope.interface`). В тестовом режиме — только заглавные латинские
  буквы (`A`, `B`, `ABC`).
- **`repository`** — в обычном режиме URL-адрес репозитория пакетов:
  схема `http` или `https`, имя хоста, без пробелов
  (`https://pypi.org/pypi`). В тестовом режиме — путь к
  существующему файлу тестового репозитория
  (`examples/repos/cycle.txt`).
- **`test_mode`** — режим работы с тестовым репозиторием. Логическое
  значение: `true`/`false`, `yes`/`no`, `on`/`off`, `1`/`0` (регистр
  не важен).
- **`version`** — версия пакета в формате PEP 440: `2.32.3`,
  `1.0rc1`, `2.0.post1`, `1.0.dev3`, `1!2.0`, `1.0+local`.
  Обязательна в обоих режимах; в тестовом режиме не используется,
  потому что в тестовом репозитории версий нет.
- **`output_image`** — имя PNG-файла, в который будет сохранено
  изображение графа. Должно оканчиваться на `.png` (регистр не
  важен) и не быть каталогом; каталог, в котором окажется файл,
  должен существовать.
- **`ascii_tree`** — режим вывода зависимостей в формате
  ASCII-дерева. Логическое значение, как у `test_mode`.
- **`filter_substring`** — подстрока для фильтрации пакетов: пакеты,
  имя которых её содержит, не учитываются при анализе. Может быть
  пустой (фильтр выключен); иначе допускаются только латинские
  буквы, цифры, `.`, `_` и `-`. Подстрока не должна совпадать с
  частью имени самого анализируемого пакета — иначе анализировать
  было бы нечего.
- **`reverse_dependencies`** — режим вывода обратных зависимостей
  (Этап 4). Логическое значение, как у `test_mode`; значение `true`
  допускается только вместе с `test_mode = true`.

`output_image` и `ascii_tree` проверяются уже сейчас и понадобятся
на Этапе 5. Вывод всех параметров в формате `ключ=значение`
требовался только на Этапе 1.

Ошибки конфигурации выводятся в stderr: заголовок с именем файла и
список всех найденных проблем, код завершения 1. Проверяются:

- чтение файла: файл не найден, вместо файла указан каталог, другая
  ошибка ОС (например, нет прав доступа), файл не в кодировке UTF-8;
- структура (с номером строки, где это возможно): параметр до
  заголовка секции, строка не является парой `ключ = значение`,
  повтор параметра или секции, неизвестная секция или нет секции
  `[settings]`, неизвестный или недостающий параметр;
- значения — по правилам выше. Пустое значение недопустимо везде,
  кроме `filter_substring`. Все неверные значения перечисляются за
  один запуск. Правила для `package_name` и `repository` зависят от
  режима, поэтому они проверяются, только если `test_mode` задан
  корректно.

### Этап 2 — сбор данных о зависимостях

**Источник данных.** Данные о версии пакета берутся из JSON API
репозитория:

```text
GET {repository}/{package_name}/{version}/json   заданная версия
GET {repository}/{package_name}/json             последняя версия
```

Для PyPI `repository = https://pypi.org/pypi`, так что для
`config.ini` запрашивается
`https://pypi.org/pypi/requests/2.32.3/json`; так же устроен
`https://test.pypi.org/pypi`. Имя пакета в адресе приводится к форме
PEP 503 (нижний регистр, разделители `-`). Запросы выполняет модуль
`urllib`: с таймаутом 10 секунд, со своим заголовком `User-Agent` и
с `Accept-Encoding: gzip` — сжатый ответ распаковывается модулем
`gzip` (у PyPI это уменьшает ответ в 3–6 раз). Если сеть не
ответила (таймаут, обрыв соединения, хост не найден), запрос
повторяется — всего до 3 попыток. Ответ разбирается модулем `json`.

**Зависимости.** Прямые зависимости версии берутся из поля
`info.requires_dist` ответа — это строки `Requires-Dist` из
метаданных пакета в формате PEP 508, например
`urllib3<3,>=1.21.1` или `colorama; sys_platform == "win32"`.
Значение `null` означает, что зависимостей нет. Каждая строка
разбирается собственным кодом на имя пакета, extras, ограничение
версии (скобки и пробелы убираются) и маркер окружения после `;`.

**Что считается прямой зависимостью:**

- зависимость с маркером, где есть переменная `extra`
  (`PySocks; extra == "socks"`), — необязательная: pip ставит её,
  только если явно запросить `requests[socks]`. Такие зависимости не
  учитываются;
- зависимость с маркером окружения (`python_version < "3.11"`,
  `sys_platform == "win32"`) — настоящая зависимость, но не для всех
  платформ. Она учитывается всегда, поэтому результат не зависит от
  машины, на которой запущено приложение;
- строка, которую не удалось разобрать, пропускается с
  предупреждением в stderr.

На Этапе 2 приложение выводило только прямые зависимости пакета;
этот вывод требовался только для того этапа и заменён графом.

**Ошибки репозитория** выводятся в stderr, код завершения 3:

- пакет не найден в репозитории;
- у пакета нет заданной версии (в сообщении — последняя версия);
- хост не найден или соединение не установлено;
- нет ответа за 10 секунд;
- ошибка проверки HTTPS-сертификата (с подсказкой, как её
  исправить, см. «Сборка и тесты»);
- HTTP-ошибка, например `HTTP error 500 Internal Server Error`;
- ответ не в формате JSON (например, указан адрес HTML-страницы)
  или повреждённый gzip;
- в ответе нет `info.requires_dist` или это не список строк.

### Этап 3 — граф зависимостей

**Обход в ширину (BFS) без рекурсии.** Граф строится от
анализируемого пакета с помощью очереди (`collections.deque`):
пакет извлекается из очереди, у источника запрашиваются его прямые
зависимости, а новые пакеты ставятся в конец очереди. Поэтому
пакеты обходятся по уровням: сначала прямые зависимости, затем их
зависимости и т. д. Каждый пакет запрашивается (скачивается) ровно
один раз: общая зависимость нескольких пакетов появляется в графе
один раз, а повторные рёбра к ней не вызывают повторной загрузки.

**Версии.** Анализируемый пакет берётся в версии из
конфигурации, а все транзитивные зависимости — в последней версии,
опубликованной в репозитории. Ограничения версий (`<3,>=1.21.1`) не
разрешаются: подбор совместимых версий — работа резолвера pip,
который использовать нельзя.

**Имена.** Пакеты сравниваются по имени в форме PEP 503 (нижний
регистр, `-`, `_` и `.` равнозначны), поэтому `MarkupSafe` и
`markupsafe` — один пакет. В выводе используется имя, под которым
пакет опубликован в репозитории.

**Фильтр.** Пакет, имя которого содержит `filter_substring`, не
учитывается: он не скачивается, рёбра к нему не добавляются, а его
собственные зависимости не обходятся (если они не нужны другим
пакетам). Подстрока сравнивается так же, как имена: без учёта
регистра, `-`, `_` и `.` равнозначны. Отброшенные пакеты
перечисляются в выводе строкой `Skipped by filter`.

**Циклы.** Обход не зацикливается, потому что каждый пакет
посещается один раз; ребро, замыкающее цикл, при этом сохраняется в
графе. После обхода циклы находятся тоже без рекурсии: в каждом
цикле есть ребро в пакет, достигнутый обходом не позже начала
ребра; если из конца такого ребра можно BFS-поиском вернуться в его
начало, ребро замыкает цикл. Каждый цикл выводится один раз,
начиная с пакета, который обход достиг первым, например
`A -> B -> C -> A`; зависимость пакета от самого себя выводится как
`E -> E`.

**Отсутствующие пакеты.** Если транзитивной зависимости нет в
репозитории, выводится предупреждение, пакет помечается
`(not found)`, а обход продолжается. Если нет самого анализируемого
пакета или пропала сеть, построение графа прекращается с ошибкой
(код 3).

**Тестовый режим** (`test_mode = true`). Вместо URL в `repository`
указывается путь к файлу описания графа, например:

```text
# комментарий
A: B C
B: C
C: A D
D:
```

- одна строка описывает один пакет: `ИМЯ: ЗАВИСИМОСТИ`;
- имена пакетов — только заглавные латинские буквы;
- зависимости разделяются пробелами или запятыми, список может быть
  пустым; повтор зависимости в одной строке не считается ошибкой;
- текст после `#` — комментарий, пустые строки пропускаются;
- пакет, упомянутый только как зависимость, считается отсутствующим
  в репозитории (предупреждение и пометка `(not found)`).

Ошибки файла (выводятся все сразу с номерами строк, код 3): нет
двоеточия, имя не из заглавных латинских букв, пакет описан дважды.
Также сообщается, если файл нельзя прочитать или он не в UTF-8, и
если в файле нет анализируемого пакета.

**Вывод.** В stdout выводится заголовок
`Dependency graph of <пакет> <версия>:` (в тестовом режиме — с
именем файла), затем по строке на каждый пакет в порядке обхода:
имя, версия и после `->` его прямые зависимости. Длинные строки
переносятся по ширине 79 символов. Ниже, если есть, — строка
`Skipped by filter '<подстрока>': ...` и раздел `Cycles:` со всеми
циклами.

Коды завершения:

- `0` — граф построен;
- `1` — ошибка в файле конфигурации;
- `2` — неверные аргументы командной строки (поведение `argparse`);
- `3` — ошибка репозитория или тестового репозитория.

### Этап 4 — обратные зависимости

**Режим.** При `reverse_dependencies = true` (только вместе с
`test_mode = true`) приложение выводит не зависимости пакета, а его
обратные зависимости — пакеты, которые зависят от `package_name`
напрямую или через другие пакеты. Вывод обратных зависимостей
требуется только на этом этапе.

**Тот же алгоритм обхода.** Тестовый репозиторий «переворачивается»:
для каждого пакета запоминается, какие пакеты от него зависят
(`invert`). Перевёрнутый репозиторий (`ReverseFileRepository`)
подставляется в ту же функцию `build_graph`, что и на Этапе 3: обход
в ширину без рекурсии не меняется, он просто идёт по рёбрам в
обратную сторону. Поэтому фильтр и циклы работают так же: пакет с
подстрокой фильтра пропускается, а каждый пакет посещается один раз.

**Только тестовый режим.** Обратные зависимости можно найти, только
зная весь граф. Файл тестового репозитория содержит весь граф, а у
PyPI нет списка пакетов, которые зависят от данного (перебрать все
пакеты репозитория невозможно). Поэтому `reverse_dependencies = true`
при `test_mode = false` — ошибка конфигурации (код 1).

**Пакеты.** Учитываются все пакеты, упомянутые в файле, в том числе
только как зависимость: у такого пакета тоже могут быть зависимые.
Если анализируемый пакет в файле не упомянут вовсе, выводится ошибка
с кодом 3.

**Вывод.** Заголовок `Reverse dependencies of <пакет> (test
repository <файл>):`, затем по строке на пакет в порядке обхода:
`D <- B, C` означает «D нужен пакетам B и C». Ниже — итоговая строка
`Packages that depend on D: B, C, A` (или `No packages depend on A`,
если от пакета никто не зависит), строка `Skipped by filter` и циклы,
записанные стрелками `<-`.

### Модули и функции

`depvis.cli` — интерфейс командной строки:

- `parse_arguments(argv)` — разбирает аргументы командной строки;
- `report_problems(title, messages)` — печатает ошибку со списком
  проблем в stderr;
- `open_source(settings)` — выбирает источник пакетов: тестовый
  файл (в обратном режиме — перевёрнутый) или репозиторий;
- `collect_graph(settings)` — строит граф, при ошибке сообщает о
  ней и возвращает `None`;
- `source_note(settings)` — пометка о тестовом репозитории для
  заголовка;
- `main(argv)` — точка входа, возвращает код завершения.

`depvis.config` — чтение файла конфигурации:

- `Settings` — неизменяемый dataclass с проверенными параметрами;
- `load_settings(path)` — читает и проверяет файл, возвращает
  `Settings`;
- `read_config_file(path)` — открывает и разбирает INI-файл;
- `describe_syntax_error(error)` — переводит ошибку `configparser`
  в сообщения с номерами строк;
- `check_layout(parser, path)` — проверяет секции и набор
  параметров;
- `find_name_problems(names)` — находит неизвестные и недостающие
  параметры;
- `build_settings(raw_values, path)` — проверяет значения и
  собирает `Settings`;
- `check_filter_against_package(values, problems)` — фильтр не
  должен исключать сам анализируемый пакет;
- `check_reverse_mode(values, problems)` — обратный режим только
  вместе с тестовым;
- `run_check(problems, name, check, *arguments)` — выполняет одну
  проверку и запоминает её ошибку;
- `describe_problems(problems)` — выстраивает сообщения в порядке
  параметров.

`depvis.validation` — проверки значений (каждая возвращает
очищенное значение или бросает `ValidationError`):

- `require_text(value)` — непустая строка без пробелов по краям;
- `parse_flag(value)` — логическое значение;
- `check_package_name(value, test_mode)` — имя пакета;
- `check_repository(value, test_mode)` — URL или путь к файлу;
- `check_repository_url(url)` — http(s)-URL с именем хоста;
- `check_test_repository(location)` — существующий файл;
- `check_version(value)` — версия по PEP 440;
- `check_output_image(value)` — имя PNG-файла;
- `check_filter(value)` — подстрока фильтра.

`depvis.repository` — запросы к репозиторию (PyPI JSON API):

- `Release` — dataclass: имя проекта, версия и строки
  `Requires-Dist`;
- `release_url(repository, name, version)` — адрес JSON-описания
  версии (без версии — последней версии пакета);
- `fetch_release(repository, name, version)` — скачивает версию
  пакета (без версии — последнюю);
- `fetch_json(url)` — скачивает адрес и разбирает ответ как JSON;
- `download(url)` — скачивание с повтором при сетевых сбоях;
- `download_once(url)` — одна попытка скачивания;
- `unpack(url, body, encoding)` — распаковывает ответ в gzip;
- `http_failure(url, error)` — ошибка по HTTP-статусу (404 — пакет
  или версия не найдены);
- `download_failure(url, reason)` — ошибка соединения, таймаута
  или сертификата;
- `missing_package_text(repository, name)` — текст «пакет не
  найден»;
- `explain_missing_release(repository, name, version)` — уточняет,
  чего нет: пакета или только версии;
- `info_object(data)`, `info_text(data, field_name)` — объект `info`
  ответа и его текстовые поля;
- `read_requires_dist(url, data)` — проверяет и возвращает
  `info.requires_dist`;
- `is_string_list(value)` — проверка «список строк».

`depvis.requirements` — разбор строк PEP 508 и имена пакетов:

- `Requirement` — неизменяемый dataclass: `name`, `extras`,
  `specifier`, `marker`; свойство `key` — имя в форме PEP 503,
  свойство `is_optional` — нужна ли зависимость только для extra;
- `canonical_name(name)` — нормализация имени по PEP 503;
- `name_matches(name, substring)` — содержит ли имя подстроку
  (сравнение в форме PEP 503);
- `parse_requirement(text)` — разбирает строку в `Requirement`;
- `split_extras(text)` — список extras из `[...]`;
- `clean_specifier(text)` — проверяет и нормализует ограничение
  версии;
- `strip_parentheses(text)` — убирает скобки вокруг ограничения.

`depvis.dependencies` — прямые зависимости из репозитория:

- `DirectDependencies` — dataclass с группами `required`,
  `optional` и `invalid`;
- `PackageInfo` — описание пакета для построения графа: имя,
  версия, имена прямых зависимостей, предупреждения;
- `RepositorySource` — источник пакетов из репозитория; метод
  `describe(name)` скачивает пакет (корневой — в заданной версии,
  остальные — в последней);
- `classify(lines)` — разбирает строки и раскладывает их по группам.

`depvis.file_repository` — тестовый репозиторий:

- `FileRepository` — источник пакетов из файла; метод
  `describe(name)` возвращает зависимости пакета;
- `ReverseFileRepository` — тот же файл «наоборот»: метод
  `describe(name)` возвращает пакеты, которые зависят от `name`;
- `invert(packages)` — для каждого пакета список зависящих от него;
- `load_file_repository(path)` — читает и проверяет файл;
- `parse_lines(lines)` — разбирает строки файла, собирает ошибки;
- `parse_line(text)` — разбирает одну строку `ИМЯ: ЗАВИСИМОСТИ`;
- `check_test_name(name)` — проверка имени тестового пакета.

`depvis.graph` — граф зависимостей:

- `Node` — пакет графа: имя, версия, ключи прямых зависимостей,
  признак «не найден»;
- `DependencyGraph` — граф: корень, пакеты в порядке обхода,
  отброшенные фильтром пакеты, предупреждения, признак обратного
  режима;
- `build_graph(root_name, source, filter_substring, reverse)` — обход
  в ширину без рекурсии (с перевёрнутым источником — по обратным
  зависимостям);
- `describe_package(graph, source, key)` — запрашивает пакет у
  источника, отсутствующую зависимость отмечает предупреждением;
- `add_edge(graph, source_key, name)` — добавляет ребро, сообщает,
  новый ли пакет;
- `find_cycles(graph)` — находит циклы;
- `close_cycle(graph, start, end, position)` — строит цикл по
  замыкающему ребру;
- `find_path(graph, start, goal)` — кратчайший путь (BFS);
- `rebuild_path(parents, goal)` — восстанавливает путь по ссылкам на
  родителей.

`depvis.report` — текстовый вывод графа:

- `wrap(text, first_indent, next_indent)` — перенос по ширине 79
  без разрыва имён;
- `arrow(graph)` — стрелка рёбер: `->` или `<-` в обратном режиме;
- `node_title(graph, key)` — имя пакета с версией и пометкой
  `(not found)`;
- `names(graph, keys)` — имена пакетов по ключам;
- `format_node(graph, key)` — строка `пакет -> зависимости`;
- `format_cycle(graph, cycle)` — строка `A -> B -> A`;
- `format_dependents(graph)` — итоговая строка обратного режима;
- `format_graph(graph, source_note)` — весь вывод Этапов 3 и 4.

`depvis.errors` — исключения: `ValidationError` (ошибка значения),
`ConfigError` (ошибки файла конфигурации, поля `path` и `messages`),
`RequirementError` (строка не в формате PEP 508), `RepositoryError`
(ошибка репозитория) и его подклассы `PackageNotFoundError` (нет
пакета или версии), `NetworkError` (сетевой сбой, запрос стоит
повторить) и `RepositoryFormatError` (ошибки тестового репозитория,
поля `path` и `messages`).

## Сборка и тесты

Нужен Python 3.10 или новее (проверено на 3.13). Приложение не
использует сторонних библиотек и не требует сборки: `run.sh`
добавляет каталог `src` в `PYTHONPATH`. Для тестов нужен pytest:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
python3 -m pytest
```

Тесты не обращаются к сети: вместо `urlopen` в них подставляется
поддельный репозиторий, а любой настоящий запрос делает тест
неудачным.

Запуск без скрипта:

```bash
PYTHONPATH=src python3 -m depvis -c config.ini
```

Демонстрационные скрипты:

```bash
./examples/demo_config.sh
./examples/demo_dependencies.sh
./examples/demo_graph.sh
./examples/demo_reverse.sh
```

- `demo_config.sh` — ошибки конфигурации (Этап 1);
- `demo_dependencies.sh` — пакеты с PyPI и ошибки репозитория
  (Этап 2, нужен интернет);
- `demo_graph.sh` — все тестовые репозитории (перед каждым запуском
  выводится сам файл) и Flask с фильтром и без (Этап 3);
- `demo_reverse.sh` — обратные зависимости на тестовых репозиториях
  и ошибка обратного режима без тестового (Этап 4, без сети).

Скорость построения графа с PyPI зависит в основном от сети: на
каждый пакет приходится один запрос. Граф Flask (10 пакетов) на
обычном соединении строится за несколько секунд.

Если Python установлен с python.org на macOS и при запросе
появляется `CERTIFICATE_VERIFY_FAILED`, нужно один раз запустить
`Install Certificates.command` из папки этого Python в
`/Applications`.

## Примеры использования

Файлы примеров:

- `config.ini` — requests 2.32.3 с PyPI;
- `examples/packages/*.ini` — pytest 8.3.3, Flask 3.0.3 (без фильтра
  и с фильтром `jinja`), Django 5.1 и certifi 2024.8.30 (пакет без
  зависимостей);
- `examples/repository_errors/*.ini` — нет пакета, нет версии,
  несуществующий хост, адрес HTML-страницы вместо JSON API;
- `examples/errors/*.ini` — по одному файлу на каждую ошибку
  конфигурации;
- `examples/repos/*.txt` — тестовые репозитории: обход по уровням
  (`levels`), цепочка (`chain`), ромб (`diamond`), цикл (`cycle`),
  несколько циклов (`cycles`), фильтр (`filter`), неописанный пакет
  (`missing`), ошибки формата (`bad_format`), общий пример
  (`basic`);
- `examples/test_mode/*.ini` — конфигурации для тестовых
  репозиториев (а также `missing_root.ini` — пакета нет в файле);
- `examples/reverse/*.ini` — обратные зависимости (Этап 4) на тех же
  тестовых репозиториях: ромб, цепочка, циклы, фильтр, пакет без
  зависимых, неописанный пакет и пакет, которого нет в файле;
- `examples/config_test_mode.ini` — `basic.txt` с фильтром `E`;
- `examples/demo_*.sh` — запускают приложение на этих примерах.

  E
  F
  G
